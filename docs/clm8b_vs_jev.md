# CLM-8B versus Jev, and what s1nav can borrow

Reviewed 26 September 2026 from the primary release:
- Hugging Face model card: `Contrastive-LM/CLM-v0.1-8B` (created 21 Sep 2026)
- GitHub repo: `Contrastive-LM/CLM` (README, `src/clm/heads.py`, `src/clm/schema.py`, `train/finetune.py`, `examples/t_rex/results/*.json`)
- The two results figures in the repo

The Notion blog was not read.

## 1. What it is

**Authors.** Kwok, Kang, Suresh, Saad-Falcon, Pavone, Ré and Mirhoseini, from Stanford (Hazy Research) and NVIDIA Research. It is released under the "Contrastive-LM" organisation, not an NVIDIA account. Weights are Apache-2.0.

**Architecture.**
- A frozen Qwen3-8B encoder (text only) produces a last-token-pooled 4096-d embedding.
- Two small MLP projection heads sit on top: one for the state, one for each candidate action. Each maps the embedding to 512-d.
- Score = exp(logit_scale) × cosine(state, action). A softmax over the candidates is the answer.
- The heads are the only trained part: about 20M parameters, a 75 MB file.

**Question types.** The Jev question types are built on the ranking primitive:
- Choice: the options are the candidates.
- Score: the ordered levels are the candidates; the answer is the expected level.
- Yes/no: a two-way softmax between the texts "Yes. This is true: …" and "No. This is false: …".

The API is TypeSafe-compatible.

**Training.** Bidirectional in-batch InfoNCE, in three stages:
1. About 60M Nemotron DQA question–answer pairs (question = state, answer = action).
2. About 30M synthetic hard negatives: plausible wrong answers generated by Gemini 2.5 Flash-Lite.
3. About 1M agent trajectory steps (ADP, Endless-Terminals, LiteCoder-Terminal-SFT), with 40% Nemotron replay.

Replay mattered: hard-negative top-1 accuracy went from 69% to 68.5% with replay, against 56.2% without. The authors also report power-law scaling of test loss, with the optimal head size at about 310 tokens per parameter.

**Speed.** The state and the actions are encoded separately, so a fixed action set is embedded once and cached. Each decision is then one state embedding plus dot products. This is where the latency gain comes from, and it grows with the number of candidates.

## 2. Performance against Jev (read from the repo's figures and result files)

**Zero-shot tests:**

| Task | CLM-8B success | Jev success | CLM latency (ms) | Jev latency (ms) |
|---|---|---|---|---|
| T-Rex game | 5/5 | 5/5 | 16.5 | 149.8 |
| Tool calling (BFCL v4) | 95.2% | 99.2% | 76.8 | 125.5 |
| WikiRacing | 26/30 | 30/30 | 79.8 | 225 |
| Super Mario | 5/5 | 5/5 | 33.5 | 132.6 |

**As a verifier picking the best of several candidate solutions (best-of-N).** CLM was fine-tuned on task-disjoint training tasks; Jev was not fine-tuned:

| Benchmark | Held-out tasks | Pass@1 of generator | CLM success | Jev success | CLM latency (ms) | Jev latency (ms) |
|---|---|---|---|---|---|---|
| DeepSWE (Opus 5, best of 4) | 38 | 73.7% | 81.6% (31/38) | 71.1% | 79 | 449 |
| Terminal-Bench 2.1 (Fable 5, best of 5) | 30 | 84.0% | 87.6% | 83.1% | 32 | 131 |

**How to read these numbers:**
1. **Accuracy.** "On par" is generous. Jev is ahead on the two tasks with real sample sizes (BFCL: 99.2% vs 95.2%; WikiRacing: 30/30 vs 26/30). The ties are on 5-run games.
2. **The T-Rex tie is mostly the harness's safety override.** A planner-based "shield" replaces any move it judges unsafe, and it was on for both models. From the result files:

   | | CLM | Jev |
   |---|---|---|
   | Shield interventions | 4,883 (over ~3,342 decisions/seed) | 28 (over ~1,119 decisions/seed) |
   | Agreement with the planner's best move | 0.658 | 0.987 |

   Survival therefore measures the combined system, as the T-Rex README itself states. On decision quality, Jev was much closer to the planner.
3. **Latency is not measured under matched conditions.** CLM ran self-hosted on one GPU (RTX 4090 in the T-Rex run; H100 for the verifier figures). Jev ran through TypeSafe's public API. In T-Rex, Jev's server-side model time was 131.9 ms; CLM's was 2.6 ms, with cached actions. The architectural speed advantage is real, but "9×" mixes it with local versus remote serving.
4. **The verifier comparison is not matched either.** CLM was fine-tuned for the task; Jev was used zero-shot. The samples are small (30–38 tasks), with no intervals reported.
5. **No calibration results.** The repo contains no calibration measurement (no ECE, Brier score or reliability plot). Its probabilities are softmaxes relative to the candidate set, as the model card's limitations note. Nothing in the release corresponds to Jev's RLCD claim of outcome-calibrated probabilities.

## 3. What s1nav can borrow

CLM-8B itself cannot be used for VLN: its encoder is text-only. The model card says a multimodal CLM-35B is "coming in early October" (unverified).

**Ideas that transfer:**

1. **Frozen-backbone, cached-feature baseline.**
   - Run the frozen Qwen3.5-9B once over the training streams, store the hidden state at every `<act>` position, and train only the heads on the stored features.
   - Each head experiment then costs minutes, not a full training run. The one-off extraction costs about 2N FLOPs per token, against about 6N per token for every LoRA epoch.
   - It shows how much LoRA adds. If frozen features come close, most ablations can run on cached features.
   - Proposed as baseline B7 and an early step in M2.
2. **Hard-negative mining for the `arrive` head.** CLM's mid-training on plausible wrong answers maps onto the GPT-6-Astra failure where a matching landmark in the wrong room triggered STOP (EP513). The simulator can generate these cases:
   - states 3–8 m from the goal with high path progress;
   - states in other rooms that contain objects named in the instruction.

   Up-sample them in the `arrive` training data.
3. **A contrastive verifier for System 2 proposals.** At an escalation, System 2 (or a later world model) proposes several candidate next-k action sequences. A CLM-style head scores each candidate's predicted end state against the instruction. This is the use where CLM showed its clearest gain (best-of-N selection). It would be an M5 option, not part of v1.
4. **Replay during specialisation.** CLM's replay result supports keeping some general data in the mix when fine-tuning. s1nav already avoids most of the risk by toggling the LoRA off for System 2. Replay matters only if the s1nav adapter is also used for anything beyond the heads.

**What not to borrow:**
- **Separate state and action encoders.** s1nav has 10 fixed macros read in one pass, so caching action embeddings saves almost nothing.
- **Relative softmax probabilities in place of calibration.** s1nav's `arrive` and `value` heads need probabilities calibrated against simulator outcomes. CLM's release does not measure calibration.
